# Nerox-Gateway 实验计划（审阅稿）

> 状态：Draft
>
> 目标：把 Nerox-Gateway 作为后端、Linux、网络、数据库、Redis、并发、分布式和排障的长期实验平台。
>
> 基线日期：2026-10-21
>
> 说明：本计划只描述实验和验证方式，不默认把 README 中的性能、高可用或集群表述当作已证明结论。

## 1. 使用方式

这份文档的目标不是把 Gateway 继续堆成一个更大的系统，而是让每一个重要结论都经过以下过程：

1. 先写出实验前假设。
2. 使用可控的假 Provider、数据库、Redis 或客户端制造一个条件。
3. 记录请求结果、时延、资源、状态变化和失败路径。
4. 对照假设解释差异。
5. 决定是否需要做最小修复。
6. 修复后重复同一个实验，确认行为改变。
7. 记录实验的迁移价值和局限。

实验名称本身不代表掌握。只有能够解释现象、拿出证据、说明替代方案和限制，实验才算完成。

## 2. 当前项目边界

当前代码已经具备这些适合做实验的边界：

- Gin HTTP API 和 SSE 流式响应。
- Provider fallback 和 API Key Pool。
- Redis Token、用户、内容缓存和 Lua 固定窗口限流。
- MySQL 用户、Token、请求日志和原子余额扣减。
- 异步日志 Channel、批量写库和 graceful shutdown。
- Docker Compose 中的 Gateway、MySQL 和 Redis。

当前项目不能单独覆盖完整的以下主题：

- Linux 内核、虚拟内存、文件系统和系统调用的完整知识。
- TCP 拥塞控制、丢包重传、DNS 和 TLS 的完整网络知识。
- MySQL 全部 SQL 优化、复杂索引设计和复制架构。
- Redis 复制、哨兵、集群、持久化和淘汰策略的完整行为。
- Kafka、Raft、Paxos、Kubernetes 控制面和多地域系统。
- 真实团队评审、线上事故、需求变化和长期运维责任。

因此，本计划优先提升业务后端中最常见的分布式问题：超时、取消、重试、部分失败、幂等、缓存一致性、共享状态、资源耗尽和故障恢复。

## 3. 实验总顺序

实验按依赖关系排列。`E13` 的测量方法从第二阶段开始贯穿所有实验，不应最后才补。

| 阶段 | 实验 | 主题 | 预计价值 |
|---|---|---|---|
| 0 | N1 | 管理接口与密钥安全边界 | 先消除明确的权限风险，并建立安全实验边界 |
| 1 | E1 + E13 | Fake Provider、故障矩阵和性能基线 | 建立可控上游和可信测量方法 |
| 2 | E2 + E9 | SSE 断开、取消和资源生命周期 | 理解请求结束条件、goroutine、连接和 fd |
| 3 | E10 + N5 | graceful shutdown 和容器资源限制 | 理解进程关闭、资源耗尽和部署边界 |
| 4 | E6 + E7 | 并发、Channel、限流和背压 | 理解原子性、有界队列和丢失取舍 |
| 5 | E12 + N2 | 缓存陈旧和旧值回填竞态 | 理解 cache-aside 与失效顺序 |
| 6 | E8 + E4 | 连接池耗尽和依赖故障 | 理解数据库等待、Redis/MySQL 降级策略 |
| 7 | E5 | 双实例和共享状态 | 理解本地状态、共享状态和横向扩展 |
| 8 | E11 + E3 | 重试、重复调用和崩溃窗口 | 理解至少一次、结果未知和幂等需求 |
| 9 | N4 | 扣费恢复方案对照 | 进入业务分布式设计和账务一致性 |
| 10 | N3 | 级联过载和重试放大 | 理解排队、主动拒绝、隔离和容量边界 |
| 11 | N6 | 双版本发布和数据库变更 | 理解兼容发布、回滚和数据演进 |

### 3.1 推荐的停止点

- 完成 N1、E1、E2 后，应该已经能解释主要的 HTTP/SSE/取消行为。
- 完成 E4、E5、E8、E12 后，应该能解释依赖故障、连接池和缓存一致性。
- 完成 E3、E11、N4 后，应该能进入业务分布式和幂等设计。
- 完成 N3 后，Gateway 作为业务 API 网关实验平台的边际收益会明显下降。
- N5 和 N6 可以根据 Linux、容器和发布方向的兴趣安排，不必为了凑数量强行完成。

## 5. 实验详细设计

## 阶段 0：安全边界

### N1：管理接口与密钥安全边界

**想验证的问题**

普通请求方是否可以调用创建用户、创建 Token、禁用用户等管理接口？Token、Provider Key、数据库密码是否被日志、响应或仓库泄露？

**实验前假设**

当前 `/admin` 路由存在，但没有挂载专门的管理认证中间件。普通请求可能直接访问管理能力。管理接口和普通 API 的权限边界尚未被测试证明。

**需要修改什么**

第一轮不修改业务代码，只使用本地数据和测试请求验证边界。第二轮才设计最小的 admin 鉴权、角色检查和密钥处理。

**如何制造故障或压力**

- 不带 Authorization 调用管理接口。
- 使用普通用户 Token 调用管理接口。
- 使用过期、禁用和伪造 Token 调用管理接口。
- 检查响应、日志、配置、Docker 环境变量和 Git 历史中是否出现明文密钥。

**观察哪些现象**

- 未授权请求的状态码。
- 普通 Token 是否可以创建用户、创建 Token 或禁用用户。
- 管理接口错误是否暴露数据库或密钥信息。
- Token 是否出现在普通日志或错误堆栈中。

**应该记录的指标**

- 每种身份和每个接口的状态码。
- 授权失败次数。
- 管理操作成功次数。
- 日志中敏感字段出现次数。

**底层原理**

认证回答“你是谁”，授权回答“你能做什么”。路由分组本身不会产生权限；缓存中的身份信息也不能代替管理角色判断。

**迁移到真实后端**

对应后台管理、租户隔离、RBAC、API Key 管理、密钥轮换和审计日志。

**局限**

本实验只能验证当前接口边界，不能替代完整的安全审计、依赖扫描和密钥管理系统。

**是否值得修复**

值得。权限边界属于明确的工程缺口，成本低、收益高。先保留实验结果，再做最小修复。

## 阶段 1：可控上游和测量基线

### E1：Fake Provider 响应矩阵

**想验证的问题**

响应头延迟、响应体延迟、慢速 SSE、429、500 和中途断流分别会触发什么行为？当前 timeout 到底覆盖哪一段？fallback 会不会重复调用？

**实验前假设**

`ResponseHeaderTimeout` 主要限制等待响应头的时间。响应头已经到达后，持续读取 body 的阶段可能没有完整的 idle timeout 或总超时。已经输出部分 SSE 后，再切换 Provider 可能造成重复内容或语义错误。

**需要修改什么**

增加独立 Fake Provider。第一轮不修改 Gateway 业务逻辑，只把 Provider URL 指向本地服务。Fake Provider 至少支持：

- 正常响应。
- 响应头延迟。
- 第一个 chunk 延迟。
- 每个 chunk 间延迟。
- 429、500、401。
- 输出若干 chunk 后断开。
- 返回超长 SSE 行。
- 记录 request ID、Authorization 和调用次数。

**如何制造故障或压力**

逐个场景执行，不要一开始同时开启多个故障：

1. 0 秒 header delay，正常 body。
2. 超过当前 header timeout 的 delay。
3. header 正常，但 body 每个 chunk 延迟。
4. 429 后恢复。
5. 500 后切换备用 Provider。
6. 输出部分内容后断开。

**观察哪些现象**

- Gateway 是否等待、超时、返回错误或切换 Provider。
- 客户端是否收到合法 SSE。
- 已经输出部分内容后是否再次收到重复内容。
- Provider 调用次数是否超过预期。
- 请求是否在 body 长时间无数据时持续占用资源。

**应该记录的指标**

- header delay、首字节延迟、chunk 间隔、总耗时。
- Provider 尝试次数和每次结果。
- 客户端收到的原始 SSE 行。
- 状态码、错误类型和已输出字节数。
- goroutine、连接、fd 和内存变化。

**底层原理**

HTTP 请求由连接建立、请求写入、等待响应头、读取响应体和关闭连接等阶段组成。一个总称为“超时”的配置，通常只覆盖其中一部分。SSE 是持续的字节流，body 阶段可能长时间保持连接。

**迁移到真实后端**

对应 Python `httpx`、FastAPI streaming response、第三方 API、反向代理和长轮询。

**局限**

本地 Fake Provider 不能完全模拟公网 DNS、TLS、丢包、拥塞和真实供应商限流。

**是否值得修复**

如果实验发现 body 无限等待、错误类型分类不合理、SSE 已输出后错误地重试，值得做最小修复。不要先把所有 timeout 合成一个未经验证的固定值。

### E13：pprof、race、benchmark 和压测基线

**想验证的问题**

当前性能数字测量的到底是哪条路径？缓存命中、缓存未命中、限流、Provider 失败和完整成功路径之间差多少？瓶颈位于 JSON、Redis、MySQL、Provider 还是日志？

**实验前假设**

单次 QPS 截图不能证明完整链路的性能。benchmark 必须在自身内部准备数据，不能依赖本地 Redis 的历史状态。pprof、race 和 trace 才能帮助解释成本来源。

**需要修改什么**

- 增加可控的 benchmark seed 和 fake Provider。
- 正确区分 cache hit、cache miss、rate limit 和 provider path。
- 如果需要，增加 pprof debug server 或专门的调试入口。
- 第一轮不做业务重构。

**如何制造故障或压力**

- 固定请求体和响应内容。
- 分别压测缓存命中、缓存未命中和限流拦截。
- 分别运行 `go test -bench`、`go test -race` 和简单 HTTP 压测。
- 在压测期间采集 CPU、heap、alloc、阻塞和 goroutine profile。

**观察哪些现象**

- benchmark 是否真的走了目标路径。
- QPS 增加时 P95/P99 是否明显上升。
- CPU、Redis RTT、DB 等待和 JSON 分配谁先成为瓶颈。
- race detector 是否发现并发访问问题。

**应该记录的指标**

- 请求数、吞吐、P50/P95/P99、错误率。
- CPU、heap、allocs/op、goroutine、block profile。
- Redis 命中率和 RTT。
- 数据库连接池等待。
- 测试数据、并发数、运行时长和环境。

**底层原理**

性能结论依赖测试路径、热身、样本量和环境。profile 用于解释成本，benchmark 用于比较变化，压测用于观察系统在并发下的尾延迟。

**迁移到真实后端**

对应容量评估、性能回归、慢请求排查和发布前基线。

**局限**

本机 benchmark 不能代表公网 Provider、真实流量分布和长期容量规划。

**是否值得修复**

值得先修复 benchmark 可重复性和观测入口。性能优化必须等 profile 指出具体瓶颈后再做。

## 阶段 2：SSE、取消和资源生命周期

### E2：客户端主动断开 SSE

**想验证的问题**

客户端断开后，Gateway 是否停止向 Provider 读取和写入？上游请求、goroutine、TCP 连接和日志是否最终结束？

**实验前假设**

`r.Context()` 的取消会传递到上游请求，但取消错误可能被当前 fallback 逻辑当作普通 Provider 故障，从而产生无意义的重试。

**需要修改什么**

第一轮不修改业务代码。使用客户端脚本读取若干 SSE chunk 后主动关闭连接。第二轮根据结果修复取消错误分类。

**如何制造故障或压力**

- Fake Provider 持续输出。
- 客户端分别在第一个 chunk、多个 chunk 和首字节前关闭。
- 增加多个并发断开客户端。

**观察哪些现象**

- Provider 是否感知取消。
- Gateway 是否继续扫描 body、继续写入或继续 fallback。
- goroutine 和 TCP 连接是否回落。
- 日志是否出现客户端取消或错误重试。

**应该记录的指标**

- 断开时机、Provider 调用次数、总耗时。
- goroutine、fd、TCP 状态和活跃请求数。
- 取消错误类型和重试次数。

**底层原理**

客户端断开会影响 HTTP 请求上下文。取消需要通过阻塞 I/O、上游 Transport 和应用层错误处理完整传播。

**迁移到真实后端**

对应 FastAPI streaming、WebSocket、长轮询、文件上传和 Celery 任务取消。

**局限**

服务端检测 FIN/RST、应用层写失败和上游取消之间可能存在时间差。

**是否值得修复**

如果取消后仍继续切换 Provider 或占用资源，值得修复。客户端主动取消通常不应被当作 Provider 故障。

### E9：goroutine、内存和文件描述符变化

**想验证的问题**

慢 Provider、慢客户端、断流和高并发请求是否造成 goroutine 泄漏、连接泄漏、fd 耗尽或内存持续增长？

**实验前假设**

每个请求都应在客户端结束、Provider 结束或 timeout 后释放相关资源。持续 SSE 和慢写入可能使资源长期占用。

**需要修改什么**

增加最小资源观测：goroutine、fd、活跃连接、请求计数和内存指标。第一轮不改资源策略。

**如何制造故障或压力**

- 大量慢速 Provider。
- 大量只建立连接但不读取 response 的客户端。
- 大量在不同阶段断开的客户端。
- 长时间运行而不是只看 10 秒瞬时结果。

**观察哪些现象**

- 负载停止后资源是否回落。
- goroutine 是否持续增长。
- fd 是否持续增长。
- heap 是否因缓存、builder 或 response body 持续增长。

**应该记录的指标**

- goroutine、heap、alloc、GC。
- 进程 fd、TCP ESTABLISHED/CLOSE_WAIT。
- 活跃请求和 Provider 请求数量。
- 资源回落到基线所需时间。

**底层原理**

阻塞 I/O、连接关闭、垃圾回收和 goroutine 退出条件共同决定资源生命周期。吞吐提高不代表资源一定健康。

**迁移到真实后端**

对应长连接、上传下载、异步 worker、WebSocket 和第三方 HTTP 客户端。

**局限**

单机资源曲线不等于 Kubernetes 或多主机环境下的行为。

**是否值得修复**

发现资源不回落、无界等待或 fd 泄漏后应修复；否则保留观测能力即可。

## 阶段 3：关闭和容器资源

### E10：graceful shutdown 时仍有活跃请求

**想验证的问题**

服务收到 SIGTERM 后，活跃 SSE、Provider 请求、日志队列和数据库写入是否按预期结束？5 秒关闭窗口内未完成的请求如何处理？

**实验前假设**

HTTP Server 的 `Shutdown` 会等待活跃请求，但 Provider、Redis、MySQL 和日志 worker 的关闭顺序可能仍有边界问题。

**需要修改什么**

第一轮不修改关闭顺序。只增加观察日志和退出码记录。

**如何制造故障或压力**

- Fake Provider 延迟 10 秒。
- 保持客户端 SSE 连接。
- 请求过程中发送 SIGTERM。
- 分别测试 1 个请求、多个请求、日志队列未刷完的情况。

**观察哪些现象**

- 新请求是否被拒绝。
- 活跃请求是否收到取消。
- Provider 是否停止。
- 日志是否刷盘。
- 超过关闭窗口后进程如何退出。

**应该记录的指标**

- SIGTERM 到进程退出的时间。
- 活跃请求数量、完成数量和取消数量。
- Provider 取消次数。
- Log queue 剩余数量和最终落库数量。
- 进程退出码。

**底层原理**

优雅关闭需要先停止接收新流量，再等待或取消旧请求，最后关闭依赖和 worker。关闭顺序本身是系统设计的一部分。

**迁移到真实后端**

对应容器滚动发布、进程重启、worker 停止和连接排空。

**局限**

本机 SIGTERM 不能完全代表编排平台的终止宽限期和负载均衡摘流流程。

**是否值得修复**

发现活跃请求被错误截断、日志丢失或依赖关闭顺序不安全时，值得做最小修复。

### N5：容器资源限制下的故障

**想验证的问题**

CPU、内存和文件描述符限制下，慢 SSE、连接堆积和数据库等待会如何影响 Gateway？进程会报错、被 OOM kill，还是只是尾延迟上升？

**实验前假设**

资源限制会改变调度、排队和错误表现。应用层 timeout 不一定能覆盖资源耗尽导致的等待。

**需要修改什么**

增加 Compose 资源限制或使用单独实验 Compose 文件。第一轮不修改业务处理逻辑。

**如何制造故障或压力**

- 限制 CPU，逐步增加并发。
- 限制内存，增加响应体和并发流。
- 限制 fd，制造连接堆积。
- 观察资源恢复和容器退出。

**观察哪些现象**

- P99、超时和错误类型变化。
- 容器是否被 OOM kill。
- fd 达到上限时的错误。
- CPU throttling 是否导致请求排队。

**应该记录的指标**

- 容器 CPU、内存、限制和 throttling。
- fd 上限和使用量。
- goroutine、连接、P50/P95/P99。
- 退出码和重启次数。

**底层原理**

容器限制会影响进程可获得的 CPU、内存和 fd。系统资源耗尽通常先表现为排队、尾延迟和错误率上升。

**迁移到真实后端**

对应容器部署、服务容量规划、资源 request/limit 和 OOM 排障。

**局限**

macOS Docker Desktop 的资源层次与原生 Linux 可能不同。需要在 Linux VM 或 Linux 主机上复核关键结论。

**是否值得修复**

适合补资源观测、合理 timeout 和 readiness；不要通过无依据地提高资源限制解决问题。

## 阶段 4：并发、队列和背压

### E6：Key Pool、日志 Channel 和限流的并发行为

**想验证的问题**

Key Pool 是否存在数据竞争？Key 分布是否符合预期？Redis Lua 限流是否在并发下准确？日志 Channel 是否有序、阻塞或丢弃？

**实验前假设**

Key Pool index 使用原子操作，应该没有直接的数据竞争。Lua 脚本在 Redis 内原子执行，但业务上的限流窗口仍需要单独验证。日志 Channel 满时当前代码可能选择丢弃。

**需要修改什么**

增加临时测试、统计和 benchmark。第一轮不改变调度算法和队列策略。

**如何制造故障或压力**

- 高并发调用 `GetNextKey`。
- 多 goroutine 并发执行限流。
- 多 worker 同时写 LogChan。
- 让消费者慢下来，逐步提高生产速度。

**观察哪些现象**

- Key 是否均匀轮换。
- race detector 是否报错。
- 限流允许数量是否超过预期。
- Channel 是等待还是丢弃。

**应该记录的指标**

- 每个 Key 的使用次数。
- race detector 结果。
- 允许/拒绝数和窗口边界。
- 队列长度、发送等待和丢弃数。

**底层原理**

原子操作只保护某个内存访问，不自动保证完整业务流程。Channel 是有容量的同步结构，Redis Lua 保证脚本内命令的原子执行。

**迁移到真实后端**

对应 worker pool、限流器、消息生产者、任务队列和多实例共享计数器。

**局限**

单实例 Key Pool 不能说明多实例下的全局公平性。

**是否值得修复**

只修复实际影响业务正确性的竞态、计数误差或不可观测丢弃。不要为了理论上的完美公平引入复杂调度。

### E7：日志消费者变慢导致队列满

**想验证的问题**

异步日志是否降低了主链路延迟？当数据库写入很慢时，队列是否堆积、日志是否丢失、请求是否仍然成功？

**实验前假设**

当前异步写日志可以让请求不等待数据库，但队列满时可能丢日志。低延迟和日志可靠性之间存在取舍。

**需要修改什么**

第一轮只在测试分支或实验配置中延迟 `flushBatch`，不直接改变生产策略。

**如何制造故障或压力**

- 延迟数据库写入。
- 提高请求速率。
- 减少 worker 数量或队列容量。
- 持续运行直到队列满。

**观察哪些现象**

- 请求延迟是否保持稳定。
- 日志是否被丢弃。
- 队列是否恢复。
- 进程关闭时剩余日志是否刷完。

**应该记录的指标**

- LogChan 当前长度和峰值。
- 生产数量、消费数量、丢弃数量。
- DB 写入耗时和错误数。
- 请求 P99 和最终日志数量。

**底层原理**

有界队列通过限制内存换取背压或丢弃。异步化只能改变等待位置，不能消除下游写入能力不足。

**迁移到真实后端**

对应审计日志、埋点、异步事件、消息生产和任务队列。

**局限**

当前日志模型较简单，不能覆盖完整审计和账务事件可靠性。

**是否值得修复**

至少应增加 dropped counter 和队列指标。是否阻塞请求、落盘或转 outbox，需要根据日志的重要程度决定。

## 阶段 5：缓存一致性

### E12：缓存过期、旧数据和数据库状态变化

**想验证的问题**

用户、Token 或余额在数据库变化后，缓存会继续允许请求多久？主动禁用后是否立即生效？内容缓存是否会返回旧结果？

**实验前假设**

用户和 Token 使用 TTL 缓存，数据库状态更新与缓存失效之间存在时间窗口。余额变化可能不会立即刷新用户缓存。

**需要修改什么**

第一轮不修改业务代码。使用现有 admin API、数据库更新和 Redis 命令观察行为。

**如何制造故障或压力**

1. 先请求一次建立缓存。
2. 禁用用户或 Token。
3. 直接修改余额或 Token 状态。
4. 在 TTL 过期前重复请求。
5. 观察恢复服务后的回源行为。

**观察哪些现象**

- 缓存命中时是否读到旧状态。
- 主动删除缓存是否覆盖所有相关 Key。
- Redis 不可用时是否回源或失败。
- 缓存内容是否包含完整请求特征。

**应该记录的指标**

- cache hit/miss。
- TTL 和实际陈旧时间。
- 数据库状态变化时间与请求生效时间。
- 回源次数和错误率。

**底层原理**

cache-aside 需要分别处理读、回源、写缓存和失效。TTL 只能限制陈旧上限，不能保证立即一致。

**迁移到真实后端**

对应权限、配置、会话、库存、配额和用户状态缓存。

**局限**

当前数据模型简单，无法覆盖复杂对象图和跨表一致性。

**是否值得修复**

权限和余额等强约束字段应明确失效策略。发现业务可绕过禁用或余额校验时值得修复。

### N2：缓存“删掉后又变旧”的竞态

**想验证的问题**

一次旧的数据库读取是否可能在另一个请求更新数据并删除缓存后，把旧值重新写回 Redis？

**实验前假设**

典型 cache-aside 读流程可能是：读缓存失败、读取数据库、等待一段时间、写入缓存。如果期间发生更新和删除，旧读请求可能重新填充旧值。

**需要修改什么**

需要增加测试专用同步点，或使用可控 fake repository。不要依赖随机 `sleep` 证明竞态。

**如何制造故障或压力**

精确控制以下时序：

1. Reader A 读缓存 miss。
2. Reader A 读到旧数据库值但暂停。
3. Writer B 更新数据库并删除缓存。
4. Reader A 继续，把旧值写入缓存。
5. Reader C 读缓存。

**观察哪些现象**

- Reader C 是否读到旧值。
- 旧值的 TTL 是多少。
- 版本号、更新时间或 fencing 信息是否存在。
- 多实例下竞态是否更容易出现。

**应该记录的指标**

- 每个操作的时间线和 request ID。
- DB 版本、缓存版本和写入顺序。
- 旧值持续时间。
- 命中率和回源次数。

**底层原理**

缓存失效不是一个瞬时全局事件。并发读回源和写缓存时，需要版本号、写入顺序、锁、短 TTL 或其他一致性策略。

**迁移到真实后端**

对应用户权限、配置、库存、价格、额度和多实例缓存。

**局限**

实验只验证选定数据的竞态，不代表所有缓存方案都需要分布式锁。

**是否值得修复**

如果旧值会影响权限、余额或计费，值得做最小版本检查或失效策略。普通内容缓存可以接受短暂陈旧时，不必过度修复。

## 阶段 6：数据库连接池和依赖故障

### E8：数据库连接池耗尽

**想验证的问题**

`MaxOpenConns` 达到上限时，新的鉴权、扣费和日志写入如何排队？连接等待如何传导到请求 P99？

**实验前假设**

数据库连接池是有限资源。慢查询或连接未释放会让后续请求等待，即使 CPU 和 Redis 都正常。

**需要修改什么**

使用临时测试程序或实验配置降低连接池上限。增加 `sql.DB.Stats()` 采集，不改业务语义。

**如何制造故障或压力**

- 执行并发慢查询。
- 降低 `MaxOpenConns`。
- 同时压测鉴权、扣费和日志写入。
- 逐步提高并发，直到等待明显增加。

**观察哪些现象**

- WaitCount 和 WaitDuration 增长。
- 请求 P99 上升但数据库 CPU 未必满。
- timeout 后连接是否正确归还。
- 日志 worker 是否反过来占满连接池。

**应该记录的指标**

- Open、InUse、Idle、WaitCount、WaitDuration。
- SQL 延迟、错误和锁等待。
- 请求 P50/P95/P99。
- goroutine 和连接数。

**底层原理**

连接池把数据库连接管理成有限资源。连接等待、SQL 执行等待和锁等待是不同层次，必须分别观测。

**迁移到真实后端**

对应 SQLAlchemy pool、Celery 数据库任务、订单服务和高并发 API。

**局限**

单个简单表不能充分练习复杂 SQL 优化。EXPLAIN、索引和死锁需要额外数据库实验。

**是否值得修复**

值得增加 DB pool 指标和操作超时。不要只通过提高连接数解决等待。

### E4：Redis 或 MySQL 运行中不可用

**想验证的问题**

Redis、MySQL 分别不可用时，鉴权、限流、缓存、扣费和日志如何表现？哪些依赖应该 fail-open，哪些应该 fail-closed？

**实验前假设**

缓存读失败可能回源数据库；限流 Redis 失败可能直接返回 500；数据库失败会影响鉴权、扣费或日志。

**需要修改什么**

第一轮不修改故障策略。用 Docker stop、网络隔离或代理工具制造故障。

**如何制造故障或压力**

- 单独停止 Redis。
- 单独停止 MySQL。
- 运行中反复停止和恢复。
- 观察恢复后缓存和连接是否重新建立。

**观察哪些现象**

- 普通请求、限流请求和缓存命中请求的状态码。
- Redis 故障是否导致所有请求失败。
- MySQL 故障是否造成请求阻塞。
- 恢复后是否有旧连接、错误重试或数据丢失。

**应该记录的指标**

- 各类请求成功率、错误率和延迟。
- Redis/MySQL 错误数。
- 回源次数和缓存命中率。
- 日志丢失数、扣费结果和重启次数。

**底层原理**

依赖故障不是单一错误。系统需要为每个依赖和每种业务操作定义降级、拒绝和恢复策略。

**迁移到真实后端**

对应缓存、数据库、配置中心、第三方 API 和消息系统故障。

**局限**

单机停止不能模拟 Redis 复制、MySQL 主从切换或跨地域网络分区。

**是否值得修复**

先明确业务策略，再做最小修复。不要默认所有依赖故障都应该放行或都应该拒绝。

## 阶段 7：多实例和共享状态

### E5：两个 Gateway 实例共享 Redis/MySQL

**想验证的问题**

两个 Gateway 实例通过负载均衡服务时，哪些状态共享，哪些状态仍然属于单个进程？停止一个实例后，服务和数据是否按预期恢复？

**实验前假设**

Token、用户、内容缓存、限流和余额落在共享 Redis/MySQL 中。KeyPool index、日志 Channel、goroutine、HTTP client 和内存缓存属于单个实例。

**需要修改什么**

增加双实例 Compose 配置和简单负载均衡。第一轮不修改业务模型。

**如何制造故障或压力**

- 启动实例 A、B。
- 使用 round-robin 发送请求。
- 观察 Key、限流、缓存和日志。
- 停止 A，再继续请求。
- 恢复 A，观察状态是否重新汇合。

**观察哪些现象**

- 请求分布是否均匀。
- 限流是否按用户全局生效。
- 缓存和余额是否一致。
- Key Pool 是否只在实例内部轮换。
- 日志是否出现重复或缺失。

**应该记录的指标**

- 每个实例收到的请求数。
- 每个实例使用的 Key 分布。
- 全局 Redis 限流计数。
- DB 余额、日志数量和缓存命中率。
- 实例停止和恢复时间。

**底层原理**

横向扩展要求跨实例状态放到共享存储，或设计明确的协调机制。本地状态不会因为启动两个进程自动共享。

**迁移到真实后端**

对应多进程服务、Kubernetes Deployment、负载均衡和无状态 API。

**局限**

两个本机容器不等于跨主机高可用，也不包含 Redis/MySQL 自身的故障转移。

**是否值得修复**

值得补 readiness、liveness 和实例标识。不要马上引入服务发现、Kubernetes 或复杂集群组件。

## 阶段 8：重试、重复调用和崩溃窗口

### E11：重试导致重复调用和重复扣费

**想验证的问题**

429、500、超时和断流后的重试会不会重复调用 Provider、重复输出、重复写日志或重复扣费？

**实验前假设**

当前重试逻辑没有完整的幂等键和账务事件模型。部分流已经发送后再重试，可能让客户端收到重复或不连续的内容。

**需要修改什么**

第一轮不增加幂等实现。Fake Provider 记录每次调用和请求标识，Gateway 只作为被观察对象。

**如何制造故障或压力**

- 第一次返回 500，第二次成功。
- 第一次 429，第二次成功。
- 第一次发送部分 token 后断流。
- Provider 成功但 Gateway 读取响应时超时。

**观察哪些现象**

- Provider 调用次数。
- 客户端是否收到重复内容。
- 余额是否扣费一次或多次。
- 日志是否记录每次尝试还是只记录最终结果。

**应该记录的指标**

- request ID、attempt ID、Provider 调用次数。
- 成功、重试、fallback 和取消次数。
- 扣费次数、余额变化和 RequestLog 数量。
- 客户端实际收到的内容。

**底层原理**

重试是“至少再执行一次”的倾向。若远端副作用已经发生但响应丢失，本地无法仅靠 timeout 判断结果。

**迁移到真实后端**

对应支付、订单、库存、任务执行、邮件发送和消息消费。

**局限**

真实 Provider 是否支持幂等键、状态查询和退款接口，需要单独确认。

**是否值得修复**

值得先修复错误分类和请求关联，再根据 E3/N4 结果设计幂等记录。不要为了“自动重试”牺牲业务正确性。

### E3：Provider 成功后、扣费前进程终止

**想验证的问题**

Provider 已经生成结果并可能产生费用，但 Gateway 在扣费、缓存或日志落库前退出时，最终状态如何？

**实验前假设**

Provider 调用、缓存写入、余额扣减和日志落库不在同一个事务中，存在漏扣费、重复扣费或结果未知窗口。

**需要修改什么**

第一轮增加可控延迟或 test-only 注入点。不要先实现 outbox 或账务流水。

**如何制造故障或压力**

- Fake Provider 返回 usage 后暂停。
- 在扣费前发送 SIGTERM。
- 在相同窗口发送 SIGKILL。
- 重启 Gateway 后重复发送同一个请求。

**观察哪些现象**

- Provider 实际调用次数。
- 余额是否变化。
- Redis 内容缓存是否存在。
- RequestLog 是否存在。
- 重试后是否再次扣费。

**应该记录的指标**

- Provider 调用时间、进程终止时间和重启时间。
- 余额、缓存、日志和请求状态。
- 重试次数和重复扣费次数。

**底层原理**

外部副作用和本地数据库更新分属不同系统，无法自然地共享一个事务。崩溃可能留下“已执行但本地未知”的状态。

**迁移到真实后端**

对应支付、订单、库存、配额、第三方任务和 Celery 任务恢复。

**局限**

真实计费 Provider 可能提供异步账单、查询或退款接口。

**是否值得修复**

值得进入 N4，但先记录原始故障窗口。修复方案应以幂等记录、账务流水、结果查询或对账为基础。

## 阶段 9：扣费恢复方案

### N4：扣费恢复方案对照

**想验证的问题**

面对“Provider 可能成功、本地扣费结果未知”，唯一请求记录、扣费流水、outbox、结果查询和对账分别能解决什么问题？

**实验前假设**

单纯给 HTTP 请求加 retry 不能保证不重复扣费。需要把请求身份、Provider 调用、扣费事件和最终账务状态分开建模。

**需要修改什么**

建议在独立实验分支中先做三种最小模型：

1. 唯一请求记录。
2. 独立扣费流水。
3. 未知状态加后台对账。

先做最小实验，不引入 Kafka。

**如何制造故障或压力**

- 在每个状态转换之间终止进程。
- 重复发送相同 request ID。
- 让 Provider 响应丢失。
- 让扣费 SQL 成功但日志或缓存失败。
- 让日志成功但扣费失败。

**观察哪些现象**

- 每个方案能否识别重复请求。
- 失败后能否恢复到明确状态。
- 是否仍存在结果未知状态。
- 对账是否能发现差异。

**应该记录的指标**

- request ID、attempt ID、ledger ID。
- Provider 状态、扣费状态、日志状态和恢复状态。
- 重复请求、重复扣费和待对账数量。
- 恢复耗时和人工介入数量。

**底层原理**

分布式事务的核心不是让所有系统瞬间一致，而是定义状态、唯一性、补偿、重试和恢复路径。Exactly-once 通常需要业务约束和可验证的幂等，而不是一句配置。

**迁移到真实后端**

对应支付、订单、库存、订阅计费、消息消费和任务状态机。

**局限**

当前 Gateway 的业务模型很小，不能代表完整账务系统，也不包含财务对账的真实数据源。

**是否值得修复**

这是 Gateway 上最值得做的深度业务实验之一。完成方案对照后再选择最小实现，不建议直接上 Kafka、Saga 或复杂事务框架。

## 阶段 10：级联过载

### N3：级联过载与重试放大

**想验证的问题**

Provider 变慢、请求涌入、数据库连接池等待和重试叠加后，系统是否形成队列堆积、重试放大和级联故障？主动拒绝、并发限制、超时和熔断分别有什么效果？

**实验前假设**

无限接收请求会把压力传递给 Provider、Redis、MySQL 和日志队列。多层重试可能使下游实际调用量大于入口流量。

**需要修改什么**

先只增加压测和观测。第二轮可在独立分支加入并发上限、请求队列、快速拒绝或重试预算。

**如何制造故障或压力**

1. 只让 Provider 变慢。
2. 只增加入口并发。
3. 只降低数据库连接池。
4. 组合 Provider 慢、入口涌入和重试。
5. 比较无限等待、固定并发上限和快速拒绝。

**观察哪些现象**

- 入口 QPS、Provider QPS 和重试 QPS 的比例。
- 等待队列是否持续增长。
- P99 是否先于平均延迟恶化。
- Redis、MySQL 和日志 worker 是否被连带拖慢。
- 拒绝请求是否能保护已接受请求。

**应该记录的指标**

- active requests、queue length、in-flight Provider calls。
- retry count、fallback count、rejected count。
- P50/P95/P99、错误率和超时率。
- DB pool WaitDuration、Redis RTT、goroutine、fd。

**底层原理**

排队系统中，入口到达率超过处理能力时，等待时间和资源占用会快速增加。重试把故障流量放大到下游，主动拒绝和隔离可以保护系统。

**迁移到真实后端**

对应 API 网关、RPC、任务队列、数据库连接池、第三方 API 和 SRE 容量管理。

**局限**

单机实验不能完整模拟多级服务拓扑、跨地域网络和真实用户重试行为。

**是否值得修复**

值得增加并发上限、重试预算或清晰的快速失败策略，但修复必须由测量结果驱动。不要在没有过载曲线前盲目加熔断。

## 阶段 11：发布和数据演进

### N6：双版本发布与数据库变更

**想验证的问题**

旧版本和新版本短暂同时运行时，数据库字段变化、缓存格式变化和活跃请求是否兼容？回滚是否会破坏旧版本？

**实验前假设**

直接修改表结构或缓存结构可能让旧版本无法读取。发布过程需要先兼容，再切换，再清理。

**需要修改什么**

创建旧版和新版镜像或二进制。增加一次向后兼容的字段变更实验，不做大规模重构。

**如何制造故障或压力**

- 旧版运行期间启动新版。
- 新版写入新增字段，旧版继续读取。
- 先执行迁移，再回滚应用。
- 在活跃 SSE 请求期间切换实例。
- 修改缓存序列化结构后观察旧缓存。

**观察哪些现象**

- 旧版是否能读取新数据。
- 新版是否能读取旧数据。
- 回滚后是否出现 500、数据丢失或缓存解析错误。
- 活跃请求是否被截断。

**应该记录的指标**

- 版本分布和请求成功率。
- 数据库迁移耗时、锁等待和错误。
- 缓存解析失败数。
- 发布、摘流、恢复和回滚时间。

**底层原理**

线上发布通常存在版本重叠期。数据库和缓存变化需要兼容旧版本，应用和数据的生命周期不能简单地绑定为一次原子替换。

**迁移到真实后端**

对应滚动发布、灰度发布、数据库迁移、缓存升级和回滚。

**局限**

本地双实例不能覆盖真实编排平台、流量治理和跨团队发布流程。

**是否值得修复**

完成前面的观测、健康检查和双实例实验后再做。它适合作为工程能力收尾实验。

## 7. 每组实验的完成标准

一组实验完成前，至少应满足：

- 能写出实验前假设和预期行为。
- 能稳定复现，而不是只成功一次。
- 有原始请求、响应或日志证据。
- 有关键指标，而不是只看最终状态码。
- 能解释现象对应的底层机制。
- 能区分代码缺陷、配置选择和实验局限。
- 能说明是否需要修复，以及修复会改变什么。
- 修复后能重复实验确认结果变化。
- 能把结论迁移到 Python/FastAPI、Celery 或 `interior-design`。

## 8. 不建议现在加入 Gateway 的内容

以下主题可以独立学习或单独建实验仓库：

- Kafka 集群和复杂消息拓扑。
- Kubernetes 全套部署和控制器开发。
- Raft/Paxos 直接嵌入 Gateway。
- 多地域多活。
- 自研服务发现、配置中心和复杂熔断框架。
- 为了“高性能”进行没有 profile 证据的大规模重构。

这些内容有学习价值，但会增加维护成本，且可能掩盖当前更值得验证的超时、幂等、缓存和资源问题。

## 9. 阶段性停止标准

当以下问题都能用实验和数据回答时，Gateway 已经完成了主要学习任务：

1. 一次 SSE 请求从客户端到 Provider、Redis、MySQL 和日志的完整链路是什么？
2. 不同 timeout 分别约束哪一段？body 长时间无数据时会怎样？
3. 客户端断开后，哪些 goroutine、连接和资源应该结束？
4. Redis 和 MySQL 分别不可用时，哪些请求应该放行，哪些应该拒绝？
5. 两个实例共享了什么，本地保留了什么？
6. Provider 成功但本地结果未知时，如何避免重复扣费？
7. 重试如何导致重复调用和级联过载？
8. 缓存为什么会陈旧，旧值如何重新回填？
9. 连接池、Channel 和 Provider 变慢时，P99 为什么上升？
10. 能否使用日志、指标、pprof、race 和压测证明自己的判断？
11. 能否说明至少两个替代方案，以及每个方案的成本和限制？
12. 能否把结论迁移到 Python、Celery 和 `interior-design`？

达到这个标准后，继续增加组件的收益会下降。下一步应把同样的实验方法迁移到更复杂的数据模型、异步任务和消息消费场景。
